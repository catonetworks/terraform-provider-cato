## Summary

Completes the Internet Firewall sub-policy lifecycle in `cato_if_sub_policy` / `cato_if_rule` / `cato_bulk_if_move_rule`, and hardens the IFW policy mutation paths against concurrent-writer races and transient backend failures. All behavior below was validated live against dev tenants (brownfield import, greenfield create, and a 4-module-instances-on-one-account stress scenario).

### `cato_if_sub_policy`: embedded cleanup rule (socket-site `native_range` pattern)

The API auto-creates a `"<name> - Cleanup Rule"` inside every sub-policy at `addSubPolicy` time (verified live; creating it as a separate `cato_if_rule` always fails with `ruleNameAlreadyExists`). The cleanup rule is now part of the sub-policy resource:

- New `cleanup_rule` nested attribute (full rule schema, Optional + Computed — omit to adopt the API default ALLOW cleanup) and computed `cleanup_rule_id`. The cleanup rule's **name is customizable**.
- **Positional identity:** the cleanup is always the sub-policy's *last* rule (max `rule.index`). Create captures it right after `addSubPolicy` (it is the sub-policy's only rule at that point); every Read/Update/Import re-resolves the last rule and refreshes `cleanup_rule_id`, so manual moves/renames in the CMA are tracked.
- Create applies a configured `cleanup_rule` body via `updateRule` in the same revision; Update pushes cleanup changes before the single publish; Delete removes everything via `removeSubPolicy`; `terraform import <sub-policy-id>` hydrates the cleanup with no extra import step.
- When the cleanup rule was manually moved off the last position and an update then collides (`ruleNameAlreadyExists`), the error now explains the cause and remediation instead of surfacing the bare API error.

### `cato_if_sub_policy` fixes

- `scope` `tracking` relaxed to Optional + Computed (the API rejects tracking settings on SUB_POLICY_SCOPE rules); when omitted, `addSubPolicy` sends the schema's documented disabled `PolicyTrackingInput` default instead of null (the field is non-nullable).
- Empty API `description` now round-trips as `""` instead of null — previously every plan forced needless replacement of the sub-policy (and cascaded into replacing all its sub-rules) because `description` is Required + RequiresReplace.
- `at` is now an input-only placement parameter, matching `cato_if_rule`: no plan modifiers, never reconciled from the API (which doesn't return positions), Read preserves the stored value and normalizes a null (freshly imported) one to `LAST_IN_POLICY`. Previously the unconditional RequiresReplace destroyed and recreated every brownfield-imported sub-policy (plus cascaded sub-rule replacements) on first apply.

### `cato_if_rule`: adopt-on-collision and orphan prevention

- Create self-heals on `ruleNameAlreadyExists`: the live rule is looked up by name (names are unique policy-wide), verified to be in the same scope (main policy vs. the plan's `sub_policy_id`; cross-scope collisions fail with a clear message since `updateRule` cannot move rules between scopes), updated to match the configuration, and adopted into state with a visible warning. Update/Delete then work natively from the adopted id — no manual `terraform import` needed for rules orphaned by interrupted applies.
- Post-mutation read-backs in Create/Update now retry transient backend failures (`Internal server error` / `DOWNSTREAM_SERVICE_ERROR`); previously a flaky read *after* a successful create+publish failed the operation and orphaned the live rule, so the next apply collided with `ruleNameAlreadyExists`.

### `cato_bulk_if_move_rule`: concurrency hardening

- `reorderPolicy` is now wrapped in a re-snapshot/rebuild retry loop: on `reorderPolicyMissingRules` / `reorderPolicyMissingSections` (rules changed between the index fetch and the reorder) and `reorderPolicyAlreadyInSession` (a concurrent writer's reorder already sits in the shared session draft — a draft accepts only one reorder before publish), the resource re-fetches the rule/section indexes, rebuilds the reorder input, and retries with backoff.
- `moveSection` / `reorderPolicy` / `publish` retain the discard-stale-revisions retry for `reorderPolicyBlockedByActiveSessions` (stale drafts left by interrupted applies or abandoned CMA sessions).
- `BuildPolicyReorderInput` now fails fast with `planned rule %q references section %q which does not exist in the policy` — previously such a row silently dropped the rule from the input and the API returned an opaque `reorderPolicyMissingRules`.

### Shared helpers (internal/provider/shared/policy)

`WithPolicyRevisionCleanupRetry`, `DiscardFirewallAndWANPolicyRevisions`, `ReorderErrLooksLikeStaleSnapshot`, `TransientAPIErr`, `WithTransientReadRetry` — all unit-tested.
